## 2. 据此补进代码的四项

### 2.1 证据访问审计（推断自第 12 页）

**为什么推断它存在**：文档强调"证据带 personID、所有提案绑定 evidenceID 以便溯源"，而且截图要 24h 失效。
一套带归属和留存期的证据体系，必然要回答"谁在什么时候读过哪条证据"，否则隔离只是嘴上说说。

**实现**：`AccessLogEntry` + `store.logAccess/listAccess`。

- 快照装配记一条 `snapshot`（actor=host）
- `get_evidence_text` 记一条 `read`（actor=agent）
- `search_evidence` 记一条 `search`
- `npm run trace -- --session` 能看到这个会话读了什么

### 2.2 人工接管（推断自第 2 / 11 页）

**为什么推断它存在**：文档说"到达上限返回友好提示，收缩任务范围"，但没说收缩之后呢。
护栏中断、设备反复失败、洞察拿不准，这三种情况都必须把会话交回人手里，否则用户只看到"服务出错"。

**实现**：`HandoffRecord` + `store.createHandoff`。

- 护栏超限 → `reason: guard-exceeded`
- 设备回执 failed → `reason: device-failed`
- `RunResult.handoffs` 直接返回给人看

### 2.3 用量计费（推断自第 15 页）

**为什么推断它存在**：第 2 页明说"防止打爆 token / 接口"，那就必须能统计每个会话用了多少。
pi 的 assistant 消息自带 `usage`，聚合一下就是账单。

**实现**：`sumUsage()`，`RunResult.usage` 带 input / output / cacheRead / totalTokens / cost。

### 2.4 证据入库管线（推断自第 3 页）

**为什么推断它存在**：文档说"先存证据再推理"，但证据从哪来、怎么去重、多久过期，属于采集那一节。
我们之前是手写 seed，这是最假的一环。

**实现**：`src/ingest/evidence.ts` + `npm run ingest`。

- `contentHash` 去重：同一张图导入两次只存一条
- 按类型设默认 TTL：截图 24h、聊天 30 天、日历 90 天、手记不过期
- **过期时间从材料产生时间算**，不是从入库时间算——否则补录一张三个月前的截图，它会从今天起再活 24 小时
- 摘要**入库时**就生成，等原文过期再想摘要就来不及了

## 5. 当前实现的整体形状（补全后）

```
采集  ingest → Evidence(带 hash/TTL/摘要) → 访问审计
        ↓
装配  MemorySnapshot（时间/时区/目标/冲突/未完成）
        ↓
推理  主 Agent（只读 + 追问 + 提案，受预算约束）
        ↓
确认  ActionCard → Outbox → 设备 → 回执（ok/partial/failed，可重试分类）
        ↓                      ↘ 失败 → 人工接管
审核  Insight Agent（过滤临时指令、登记冲突）
        ↓
写入  MemoryDoc（generation CAS）
        ↓
观测  trace（消息/访问/问卷/压缩/用量/接管）
```
