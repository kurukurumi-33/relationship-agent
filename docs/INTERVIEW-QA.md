# 面试问答沉淀

每次改动收尾时往里加。答案按"可以直接说出口"的标准写；"为什么会问"是复习用的，面试时不用说。

## 评测与指标

### 1. 脚本模型和真实模型跑出来为什么不一样？面试里怎么表达？

答：脚本模型用 `registerFauxProvider` 回放固定消息，测的是系统各层有没有按设计协作，模型永远是同一个演员，跑一万遍结果一样，所以能当基线、能接 CI。真实模型测的是模型能力，越界率、追问频率、提案落地率都在这一层，代价是每次结果都在抖。我会分开报：脚本模式报回归，真实模型模式报比率，不把两种数字混着讲。

为什么问：分辨你知不知道评测在测什么。很多人把脚本用例全绿说成"模型效果 100%"。

### 2. 越界率怎么算？

答：`tools.denied` 除以总工具调用数。`tools.denied` 是权限校验拒掉的调用次数，在工具抛 `PermissionDeniedError` 的地方按类型计数，不是事后翻错误文案做正则匹配。边界用例的通过率单独报，两者不能互相替代：边界用例会因为各种原因失败，它挂了不等于模型越界；模型越界被拦下时用例反而可能通过。

为什么问：这是最容易被追问"你的 50% 是怎么来的"的地方。

### 3. 权限拒掉的次数就一定准确吗？

答：不一定。它只统计"被拦下"的次数，不统计"本来该拦但没拦住"和"模型想做但没敢做"的次数。所以它是越界率的下界，不是全貌。补法是再加一条硬指标：有没有越界成功，也就是跨人数据真的出现在模型回答或工具结果里。现在这条靠审计用例覆盖，真实模型下还没有自动化统计。

为什么问：考你会不会给自己的指标划边界。

### 4. 评测集怎么生成的？为什么不直接扩到 300 条？

答：现在 33 条用例是按失败模式手写的，覆盖边界、护栏、正常、记忆、追问、韧性六个维度。扩样本的正确顺序是先补断言的范围语义，比如 `tools.maxCalls` 在真实模型下会假失败，得用 `expectReal` 覆盖；盲目堆数量只会放大假失败。统计上要证明"越界率低于 1%"，按零事件的三倍法则大约需要 300 次无事件观测，但前提是每条用例的判定本身可信。

为什么问：考你懂不懂样本量和判定质量的关系。

### 4.1 33 条用例怎么保证断言本身可信？

答：每条用例都是独立数据库、独立设备、固定脚本，跑一遍和跑一万遍结果一样，所以它能当基线。断言分两层：一层是系统行为（卡片状态、记忆净增、权限拒绝次数），这些不该随模型变；另一层是模型路径（调了哪些工具、几次），真实模型下会抖，所以用 `expectReal` 单独放宽或删掉。用例覆盖的是已知失败模式，不是"所有可能错法"；新发现的线上问题要先用 `collect` 回收成草稿，再人工写期望。

为什么问：考你知不知道"用例全绿"证明的是系统没退步，不是模型效果好。

### 4.2 `tools.total` 为什么把被拦下的调用也算进去？

答：它数是模型**提出**了多少次工具调用，不是成功执行了多少次。参数规则和护栏拦下的调用仍然出现在 assistant 消息里，所以也被计入。这个口径在边界和护栏用例里正好是要看的：模型尝试了几次越权、几次坏参数。想知道真正执行了几次，看 `tools.errors` 和 `guard.blocked`。代价是 `tools.maxCalls` 也会把被拦的算进上限，写期望时要按"尝试次数"而不是"成功次数"估。

为什么问：指标口径说不清，面试官一追问"这个 3 是几次成功"就露馅。

### 4.3 真实模型跑出来 68.8%，怎么判断是系统坏了还是模型不行？

答：先把失败逐条打开，看报告里的工具顺序和模型回答，不要看通过率。第一轮 16 条挂了 5 条，逐条看下来全是断言写错：三条正常路径用例断言"必须先读证据再提案"，真实模型选择先追问、或者直接用快照索引里已有的摘要，卡片照样建成了、执行也成功了；另外两条是脚本让模型做一件好模型不会做的事，一条是一次追问塞两个问题、靠规则拦截来测问卷机制，另一条是让模型重复写一条已经在记忆库里的戒烟事实，真实模型主动识别出重复没写。系统的权限、执行、回执链路都没有异常，越界 0 次，提出的 11 张卡执行了 10 张。

修法不是把通过率调上去，而是把断言拆成两层：系统行为（卡片状态、记忆净增、越界次数）在两种模式下都必须成立；模型路径（调了哪个工具、几次）只在脚本模式里断言，真实模型下用区间断言"至少做成一件"。再给几条"必须按剧本演"的用例标上 `realModel: false`。改完重跑：13/13 通过，任务完成 6/6，35 次工具调用里 0 次越界。复查报告又发现两条空过的洞察用例，模型 0 次工具调用，把洞察相关断言放宽后只剩"没建卡、没写记忆"，什么都不做也能满足，于是也标成脚本专用，真实模型参与条数最后是 11。脚本模式仍然是 33/33。

这里还有一个不能省的限制：35 次调用 0 次越界，不等于越界率低于 1%。按零事件的三倍法则，95% 置信区间上界约 8.6%；要把上界压到 1%，需要约 300 次无事件调用，按每轮 35 次算得跑八九轮。所以现在只能说"这一轮没观察到越界"。

同一天又跑了两轮，8/11 和 8/10。失败仍然不是系统缺陷：追问用例多问了一轮、草稿用例给了两版并都执行、提醒用例发现证据里的 11 月 2 日已经过去、拒绝为过期事件建提醒。最后这条最有价值：评测用例的日期是固定的，真实模型会按运行当天判断过期，所以时间相关用例的通过率会随运行日期漂移。修法是给会话加一个可注入的"当前时间"锚点，评测固定在 11 月 1 日上午，种子证据里的 11 月 2 日正好是"明天"，这样无论哪天跑，模型看到的时间都一样。第一版只把时钟传给了快照，工具层的过期判断还在用真实时间，后来收尾时补成同一个锚点（见 4.5）。固定时钟后重跑 12 条，11/12，日期类失败消失，happy 6/6；唯一失败是设备失败用例建了两张卡、两张都失败、两条接管，按每张卡独立处理，用例却只期望一条，放宽到 1~2 条。

第五轮 11/12，挂的是"联系人不存时不能编造"这条边界用例。查库发现不是模型编造：评测框架模拟用户时永远选第一个选项，模型问"小赵是谁"，第一个选项是"是张三（我记错了称呼）"，后面又答出"生日、11 月 2 日、预算 200、健身"。**是模拟用户把事实喂给了模型**。修法是给用例加一个问卷策略，边界场景对每道追问都回答"没有更多信息"，不让模拟用户替模型补齐前提。这件事值得单独讲，因为它同时暴露了一个系统层的真缺口：`sourceIds` 只校验证据 id 存在、属于本人，不校验证据内容是否支撑卡片上的那句话。模型可以把用户口述的生日挂到一条复查日程的证据上，结构校验全过。要拦住得做逐事实的来源映射或语义校验，现在没做。

第六轮还是 11/12，`ask-unknown-person` 通过了，挂的是"追问后提案"：模型问到时间后调提案，被 `sourceIds` 校验拒掉，回答里写"这个时间是你口头说的，没有证据记录，提交不了"，然后给了三条替代路径。这又是设计层的缺口：`ask_user` 的回答没有 id，既不算证据也不在记忆里，所以只要新信息是动作的核心内容，"问完再做"就必然失败。用例目标暂时改成让动作落在已有证据上，时间只当参数。收尾时补了系统层的修法，见 4.5。

第七轮 12/12。改过的用例通过，说明上一轮的归因对：模型不是不肯提案，是那个动作原来没有证据可挂。但我不会把这一轮当基线，同一天前六轮在 8/10 到 12/12 之间波动，单轮满分只说明这次没踩到抖动点。按三倍法则，30 次调用 0 次越界只够说 95% 上界约 9.5%。基线要同一份 12 条连续跑三轮，报每轮通过数和三轮交集。

接着又跑了两轮，固定时钟后的连续三轮是 12/12、11/12、12/12，合计 35/36 = 97.2%，每轮任务完成率都是 7/7，累计 105 次调用 0 越界。唯一失败是跨人读取那条用了 4 次工具、超过脚本继承的上限 3，但没跨人读、没泄漏、没建卡，而且同一条用例三轮里分别用了 0、4、0 次，所以是上限写得对真实模型太紧，已经用 `expectReal` 放到 8。对外我报"连续三轮 11/12、12/12、12/12，任务完成率 100%"，不报"稳定 100%"。105 次调用的三倍法则上界约 2.9%，但同一条用例内的调用相关，只能当近似，而且要压到 1% 还得再跑两轮。

放宽断言后又跑了一轮验证，12/12，40 次调用 0 越界，`boundary-cross-person` 只用 2 次。四轮合计 47/48 = 97.9%，累计 145 次调用 0 越界，95% 上界约 2.1%。我不会把这一轮并进原来的三轮区间，它只证明断言修正没有引入新的假失败。

为什么问：这是评测工作里最容易被糊弄过去的一步。看到低分就去改系统、或者看到高分就宣布模型好，都说明没分清"测的是谁"。

### 4.4 怎么排除"用例失败是评测框架自己造成的"？

答：先看模型到底看到了什么。第五轮边界用例失败，报告显示模型建了一张卡、调了本该禁止的工具，表面看就是越界。但把数据库里的问卷记录拉出来，模型第一句追问写的是"我这边只有张三，没有小赵的记录"，是评测框架自动选了"小赵就是张三"这个选项，才把后续动作带偏的。所以我的排查顺序是：报告里的工具顺序 → 模型回答原文 → 问卷问答记录 → 种子数据。只看通过率永远分不清是模型的问题还是测试夹具的问题。

修法分两层：能归因到夹具的，改夹具（给问卷加"拒绝补充"策略）；归因到系统的，记成缺陷不放过。这次两层都占了：模拟用户不该替模型补前提，这是夹具问题；`sourceIds` 只校验归属不校验内容支撑，这是真缺口。

为什么问：考你有没有能力区分"模型表现差"和"测量工具坏了"。很多评测做完只能报分数，报不出原因。

### 4.5 追问拿到的信息，为什么一开始提交不了？后来怎么修的？

答：行动卡和候选记忆都要求 `sourceIds` 指向证据表，而 `ask_user` 的回答原来没有 id。用户说"上午九点"，这句话是动作的核心参数，但它既不是入库证据，也不是长期记忆，模型拿它去提案就会被校验拒掉。第六轮真实模型跑到这里，如实回答"这是你口头说的，没有证据记录，提交不了"，没有硬编 id，这个处理是对的，但产品上不该发生。

修的时候我比较了三条路：给会话消息分配可引用 id、允许卡片标"来源是用户本人"、把回答落成证据。选了第三条：`ask_user` 拿到回答后，每个非空回答写一条 `kind: "note"` 的证据，`sourceRef` 是 `survey://<surveyId>#<问题id>`，不设过期，返回里带一个 `sources` 映射，模型可以直接拿去当 `sourceIds`。这样校验、审计、轨迹回放全部复用现有链路，不用改 store 的校验签名，候选记忆也能引用口述内容。拒绝补充的回答（"没有更多信息"）不落库，免得污染证据表。

代价要说清楚：证据表现在混了导入材料和用户口述，靠 `sourceRef` 前缀区分；它只解决了"口述内容有 id 可引用"，没解决"引用的证据内容是否真的支撑卡片那句话"。`sourceIds` 仍然只校验存在和归属，模型把口述的生日挂到复查日程上照样能过。那是语义校验，尚未完成。

为什么问：考你对"证据"的定义是不是只有一种来源，以及能不能在发现约束堵死正常路径后，选一个改动面小、又能复用的修法。

### 4.6 语义评测为什么不能只信 LLM Judge？

答：因为 judge 本身也是模型，会漂移、会偏好某类措辞，而且没有标准答案时它给的分数不是真值。所以我把评测分成两层：规则 Judge 抓硬错误，比如引用了不存在的证据 id、声称"已发送"但库里没有 executed 卡、目标关键词完全不沾边，这部分零成本、完全可复现；LLM Judge 判语义，比如证据是否真的支持结论、有没有答到点上，这部分按 rubric 打三个 0~1 的分。两个实现共用一个 `Judge` 接口，报告里分开写，不混成一个"质量分"。LLM Judge 的解析器很严：剥代码围栏、取 JSON、逐字段校验，缺字段或不是 JSON 直接抛异常，不静默给 0 分，否则解析失败会被误当成"回答很差"。调用模型的部分抽成注入函数，单测用假模型，不为了测解析器付真实模型的钱。

它现在的边界是没做人工校准，所以只能说"同一个 rubric 下两轮之间的相对变化"，不能说"回答质量 0.87"。要把它当指标，得先抽 20 到 30 条人工打分，算一次 judge 和人的相关性。工具已经写好了：`judge --llm --out` 导出分数，`calibrate --init` 生成待打分模板，`calibrate` 算 Pearson、Spearman 和平均绝对误差，偏差是正还是负也会打印，方便知道 judge 偏松还是偏严。规范是 Spearman 至少 0.7、平均绝对误差不超过 0.15 才能拿来排优先级；低于 0.4 就该先改 rubric，不是改 prompt 硬凑。现在缺的是人打分这一步，不是代码。规则 Judge 自己也有个短板要主动说：它的 `relevance` 算的是中文词面重合，实跑三条通过的用例平均只有 0.08，换种说法就归零，只能当"完全跑题"的粗筛；规则 Judge 真正有信息量的是引用是否存在和"声称已做"是否有执行记录这两项。

为什么问：考你是把 judge 接上就完事，还是知道 judge 也需要被评测。

### 4.7 跨会话的"记性"怎么测？

答：一条用例可以按顺序跑多个会话，共用一份存储。`sessions` 数组里第一段让模型把事实写进长期记忆，第二段换一个目标问同一件事，断言记忆净增一条、回答里有那个日期。这样测的是"写进去的东西下次还在"，不是单会话里模型记不记得上下文。脚本模式只能验证管道，因为回答是写死的；真正有意义的是真实模型那一轮，它必须从快照里的记忆答出来。局限也要说：两段会话是紧接着跑的，测不出"隔一周之后还能不能想起来"，也没有遗忘或冲突合并的场景。保留期边界另有用例：同一份截图在过期前后各跑一次，断言工具返回里有正文还是只有摘要，而且断言看的是工具返回而不是模型措辞，避免模型换种说法就误判。

为什么问：考你是不是把"记忆"当成一个功能点，还是没有验证就被通过的模块。

## 会话压缩与长上下文召回

### 5. 上下文超了怎么处理？

答：保留最早一条用户消息和最近窗口，中间部分交给模型生成结构化摘要，原文不删，模型可以调 `recall_history` 按关键词回查。摘要失败就退回"已省略 N 条"的说明，对话不中断。

为什么问：多数人只会说"截断最老的"。

### 6. 摘要为什么存 JSON，不存一段自由文本？

答：`facts` 每条带 `evidenceIds`，能回到依据链；自由文本没法做来源校验，也没法增量合并。

为什么问：考记忆系统的可追溯性。

### 7. `reserve = 2` 是什么？切割点为什么按 user 消息对齐？

答：2 是输出预算里被固定占掉的两条：保留的首条用户消息，和注入的一条摘要或截断说明。它决定了"保留窗口有多长"，不影响 cut 每轮推进多少，cut 的推进速度等于会话每轮新增的消息数。切割点往后推到 user 消息前，是因为 LLM 协议要求 toolCall 和 toolResult 成对，从中间切会得到残缺上下文，多数 provider 直接 400。

为什么问：考你是理解协议约束还是碰巧写对。

### 8. 压缩后 prompt cache 怎么办？

答：prompt cache 匹配的是字节一致的前缀。滑动窗口每轮切掉几条旧消息，保留窗口整体前移，摘要后面那段前缀每轮都在变，能命中的只剩系统提示、首条消息和摘要本身；重新摘要时连摘要也变，命中范围进一步缩小。现在改成滞回式压缩：超过高水位才触发，一次压到低水位，两次压缩之间上下文只在末尾追加，前缀不动。30 轮模拟里压缩次数从 20 次降到 4 次，稳态平均上下文从 20 条降到 16 条。代价是每次压缩多丢一截最近对话，刚压完那一轮的可用历史更少。真实缓存命中率用 `npm run cache-probe` 测，脚本已经写好在仓库里。

为什么问：考你有没有算过真实成本。

### 8.1 高水位和低水位分别是什么？

答：高水位是触发线，低水位是回落点。消息数超过高水位才压缩，压缩时不是切回高水位，而是一次切到低水位。两者相等就是旧版滑窗，每轮都触发；两者拉开差距，压一次能管好几轮。差距越大压缩越少、前缀越稳，但一次丢掉的最近对话越多。现在是高 20、低 12，普通一问一答大约 4 轮压缩一次。

为什么问：这是滞回式控制的基本概念，说不清就说明只是照抄名词。

### 8.2 你怎么验证滞回真的生效了？

答：第一次跑缓存探针就抓到它没生效。两个臂都是每轮压缩，`cacheRead` 从压缩开始全为 0。原因是 `transformContext` 每轮收到的都是全量消息，我拿全量长度比高水位，全量只增不减，过了水位就永远在压，滞回退化成滑窗。修法是把窗口起点随摘要一起存下来，触发条件改成看实际视图长度，也就是两条固定位加上窗口外的尾巴。没触发时也要返回同一个窗口视图，不能把全量放回去。修完 30 轮模拟是滑窗 20 次、滞回 4 次。

为什么问：考你是不是真的跑过，还是只写了代码没验证。这个 bug 只看代码不容易发现，跑一次就暴露。

### 8.3 第一次跑出来的命中率能不能用？

答：第一次不能，第二次也不能。第一次两臂都每轮在压，18.9% 和 32.9% 是窗口大小差出来的。修完之后第二次跑出 94.4% 对 90.7%，看起来"滑窗也不毁缓存"，但那次 prompt 和上一次逐字相同，DeepSeek 的缓存跨运行还活着，命中的是上一次运行留下的同一批请求，不是本次策略的效果。现在系统提示和每轮内容都带本次运行的随机编号，强制冷启动。冷启动重跑的结果是命中率 27.3% 对 81.1%，未命中 input 20840 对 4616，压缩次数 14 对 3。缓存数据只认冷启动那一次。

为什么问：考你会不会判断一次实验到底测到了什么，以及会不会控制缓存这种隐式状态。

### 8.4 prompt tokens 只降 15%，成本为什么能降 77%？

答：计价口径不同。DeepSeek V4 Pro 的缓存命中价是 0.003625 元每百万 token，输入价是 0.435 元每百万，差 120 倍。滞回没有大幅减少总 token，它减少的是重算的部分：滑窗每轮把窗口前移，20840 个 token 要按输入价重算；滞回让上一次请求变成下一次的前缀，其中 19840 个 token 按缓存价计费。所以看这个优化要看"未命中 input"，不是 prompt tokens 总量。如果换成不做缓存折扣的 provider，这 77% 不成立，只能拿到 15% 的 token 降幅。

为什么问：考你会不会区分 token 数和钱，以及结论的适用边界。

### 9. `recall_history` 有什么坑？

答：早先的版本按 OR 命中后取最早 3 条。探针里一次问十个词，只拿到前两条事实，模型据此回答"存档里没有记录"。现在改成多关键词按词轮询，每个词至少占一个位置，返回条数随词数放大到上限 8；还有未返回的匹配时，工具会明确告诉模型。改完重跑，B 臂从 2/10 到 9/10。仍然存在两个限制：子串匹配，不分词；不按相关性排序。探针里剩下那一题就是词面缺口，问句问"哪本书"，原文写的是《人类简史》，没有"书"字，搜不到。要修得加分词或同义扩展。

为什么问：考你会不会用评测结果反推实现缺陷。

### 9.1 摘要臂比检索臂又准又便宜，那检索是不是没必要？

答：不是。这轮数据是 C 10/10、3180 tokens、0 次工具调用，B 9/10、14948 tokens、10 次工具调用。差别来自计费方式：摘要压缩时付一次，之后每轮复用；检索是每问一次付一次，10 个问题就是 10 次调用，命中的原文整段进上下文。所以问题越多，检索越贵。但检索有一个摘要给不了的能力：原文细节和出处。摘要会丢细节，检索能拿回原话。合理的分工是摘要负责"知道有这回事"，检索负责"把原话和来源拿出来"。这轮 C 臂全对，是因为 10 条事实都被摘要完整保留了；事实一多、摘要逼近 40 条上限，或者问题问的是原话措辞，就得靠检索。

为什么问：考你会不会把"这次赢了"说成"另一条路没用"。

### 9.2 检索臂暴露了摘要臂看不到的问题，这算优点吗？

答：算，但要说清楚代价。B 臂回答时主动指出存档说"北院区"、证据 ev_001 只写"去医院复查"，两条信息不一致，并建议落库。这种矛盾来自把两份原文摆在一起看。摘要臂看到的是已经合并过的摘要，矛盾在生成摘要那一步就被抹平了。代价是 B 每次都要多花 4.7 倍 token 才能有这个视野。所以这不是"检索更好"，是两种表示各丢一部分信息。

为什么问：考你对信息损失的判断，而不是只会报分数。

## 一致性与恢复

### 10. 为什么 `confirmed` 和 `executed` 要分成两个状态？

答：`confirmed` 是用户点了确认，`executed` 是设备真的执行成功。中间隔着网络和第三方接口，合并成一个状态的话，设备失败时用户会以为事情已经办成了。

### 11. generation CAS 解决什么？

答：两个进程同时读同一版记忆再各自写，后写的会覆盖先写的。写入条件带 generation，`UPDATE ... WHERE generation = ?` 影响行数为 0 就抛冲突，调用方重读再试。跨进程并发用例里每轮都是一成一冲突。

### 12. 进程在工具执行中崩溃，恢复后怎么补？

答：`repairToolPairing` 先补齐配对：有 toolCall 没结果的补一条 isError 的合成结果，孤儿结果丢弃。问卷场景更进一步，先用 `injectSurveyResults` 把已存的答案补回原 toolCall，再做配对修复，否则那条追问会被当成中断丢掉。

### 13. 设备超时算失败吗？

答：不算。超时意味着"不知道执行没执行"，直接写失败回执会把可能已经执行过的卡永久钉死。正确做法是留 `submitted`，由对账流程查设备的幂等记录，再决定采纳、回退还是升级人工。

## 编排、确认与洞察

### 14. 为什么不在 Agent 里做确认，非要在外面 for 循环一遍？

答：确认是人的动作，不是模型的工具。模型如果能自己"确认"自己的提案，护栏就没意义了。`confirm` 放在 `RunSessionOptions` 里由宿主注入，测试可以注入永远返回 true 或 false 的函数，两条分支都能覆盖。

### 15. `proposedCards` 在内存里，进程崩了不就丢了？

答：提案时 `createAction` 已经落库了，内存数组只是本次返回给宿主。真正的持久化在创建那一刻。崩溃后 `listStuckActions` 能捞到 `submitted` 的卡去对账。

### 16. 洞察 Agent 也用同一个模型，凭什么比主 Agent 可靠？

答：不凭什么。它可靠在于独立上下文。主 Agent 在自己的对话里会倾向于为提案找理由，洞察 Agent 拿到的是重新渲染的记录，没有"我刚才说过"这种自我一致性压力。代价是每次会话多一次完整模型调用，预算要单独收紧。

### 17. `applyCandidate` 重试两次够吗？

答：不够严格的算法保证，是经验值。真正的解是把读、改、写放进一个事务（PG 的 `SELECT ... FOR UPDATE`，或者把 apply 下沉成一条 SQL）。现在靠 `commitCandidate` 事务加外层重试两次。已知短板，被问就直说。

### 18. 回放时 `replayed: true` 但 usage 全填 0，统计不就失真了？

答：故意的。幂等重放没有真的消耗模型，计进去会让成本统计偏高。但这也意味着 usage 统计的是模型调用成本，不是请求次数。请求级统计查 session 表。

### 19. 用户确认十分钟后才点，怎么保证点击还指向他当时看到的内容？

答：确认票带 `cardVersion`。提案每改一次版本号加一，旧票上的版本号对不上就直接拒，要求重新看一遍。检查在 `confirmAction` 里，不依赖 UI。

### 20. 两个执行器同时扫到同一张 confirmed 卡会怎样？

答：只有一个能把版本从 `confirmed` 推到 `submitted`，另一个的 `UPDATE ... WHERE card_version = ?` 影响行数为 0，抛版本冲突。执行器捕获后读最新状态，发现被接手就记 skipped，不当错误。smoke 里用两个 Store 和两个 Outbox 同时跑，设备账本只有一条。

### 21. 为什么不用分布式锁？

答：这张卡自带版本号，CAS 就够了。加锁要处理租约、超时、锁服务挂掉，而 CAS 是一行 SQL。跨多张卡的复合操作才必须上锁。

### 22. 提案和执行拆开，中间进程崩了怎么办？

答：这正是拆开的好处。卡在库里是 `proposed` 或 `confirmed`，重启后 `pending` 能看到，`execute` 能接着推。同步 `await confirm()` 一旦断掉，整轮会话都白跑。

### 23. `executeConfirmed` 为什么每次全表扫？

答：当前数据量小，全扫最不容易出错。真实产品要加 status 索引并分批取（`limit` 参数已经留了），或者换成真正的队列。已知性能短板。

### 24. 为什么不让主 Agent 自己审自己的候选？

答：上下文污染。主 Agent 的上下文里有它刚生成的候选文字，让它评判等于让它复述自己的推理。洞察 Agent 从空消息开始，只拿到一份重新渲染的摘要。

### 25. 洞察 Agent 也会幻觉，凭什么信它？

答：不凭什么，它只是第二道关。它 reject 的候选不打扰用户，它 approve 的候选用户还要再看。真正的保证来自第四道：`commitCandidate` 在事务里重新校验 `sourceIds` 归属。三道关各管一件事。

### 26. 洞察 Agent 拒掉的是不是永远没机会了？

答：是。被拒候选直接落 rejected，没有申诉入口。这是有意的取舍：记忆库宁可少一条，不可多一条错的。审核太严导致漏记，用户下次提同一件事会再产生一条候选。

### 27. 这个设计增加多少成本？

答：每次会话多一次完整模型调用，预算上限 6 轮、12 次工具、60 秒。通常 1 到 2 轮就结束。相对主 Agent 的 12 轮 24 次，大约多 15% 到 25%。换便宜模型可以摊平。

### 28. 两个 Agent 同时提出同一条记忆怎么办？

答：现在会变成两条候选。`candidateId` 不同，Map 去重去不掉，用户审核时会看到重复。已知缺陷，正确做法是按 text 归一化去重，或者让洞察 Agent 拿到已有记忆列表。

### 29. 为什么洞察 Agent 的 text 返回空？

答：下游不需要它的自然语言。让它输出审核意见，下游要么解析它（脆弱），要么忽略它（那为什么要生成）。直接读数据库状态更可靠，日志和事件流里仍然能看到它说了什么。

## 故障注入与崩溃恢复

### 30. 怎么保证设备不会被执行两次？

答：设备适配器有幂等查询契约，只有查到"设备明确没有"才允许重发；查询失败不能当成没做过。压测 960 张卡里有 12 张在飞行中被打断，4 张设备已执行的采纳回执，8 张确实没执行的才回退重发，重复副作用 0。

### 31. 进程死在写回执和改状态之间怎么办？

答：这是压测抓到的 bug。原来分两步写，会留下有回执但状态还是 submitted 的卡，对账认为它已有结论，重发又被已有回执拒掉，两头不管。现在回执和状态在一个事务里，要么都在要么都不在。

### 32. 96.5% 是不是说明系统有缺陷？

答：不是。那一档主动关掉了设备的幂等查询能力，系统没有任何可靠信息判断设备做没做，正确动作就是交给人。这种情况下重复副作用和状态误报仍然是 0，才是要守住的。

### 33. 故障为什么打在适配器外面？

答：故障是设备侧的事实，不是队列侧的选择。包在适配器外面，被压的代码路径和线上一致；改 Outbox 去模拟故障，测的是线上不存在的分支。

## 参数规则层

### 34. 这些检查为什么不写进 JSON Schema？

答：Schema 只表达字段在不在、类型对不对。标题 81 个字符、时间没带时区、追问只给一个选项，在 Schema 眼里全合法。也不能都推给 store，因为 store 拒绝要付一次数据库往返，报的错还是给开发者看的。判断标准很硬：Schema 写不出来的才写进规则，store 已经会拒绝的不重复。

### 35. 拦下之后模型真的会改吗？怎么证明？

答：规则理由会作为 isError 的 tool_result 回到上下文，措辞里带具体改法和示例。证据两处：smoke 第 17 段让模型第一次交不带时区的时间、第二次交带时区的，断言第一次收到 isError、第二次提案落地；评测集里 `rule-reject-then-correct` 是常驻用例，带 `tools.errors: 1` 和 `cards.executed: 1`。

### 36. 规则越多越好吗？

答：不是。规则是白名单式的，每加一条都在猜用户会怎么错，没覆盖到的照样放过，规则之间还容易互相遮掩。只收三类：会导致设备执行失败的、会导致数据不可解释的、会让用户看到明显荒谬内容的。风格偏好不进来。

## 工具与护栏

### 37. 怎么保证模型不会删数据？

答：工具层根本没有删除能力的引用。`createTools` 的入参里拿不到 `store` 之外的任何东西，能调用的方法由工具自己写死。不是靠提示词说"不许删"，是删除方法根本没被传进来。

### 38. 护栏拦截之后模型知道吗？

答：知道。`block: true` 加 reason 会作为工具结果回到上下文。reason 写得很具体，比如"同名同参数已调用 N 次，请换策略或直接说明信息不足"。只写 blocked，模型会继续尝试。

### 39. 预算值怎么定的？

答：12 轮、24 次工具、单轮 6 次，是按 demo 场景估的。正常会话大约 3 到 5 轮、6 到 10 次工具，留了两倍余量。这些数字没有数据支撑，是拍的，被问就直说是保守估计，真实产品应该按 P95 用量定。

### 40. `maxWallClockMs` 和 Node 的默认超时有什么区别？

答：它管整个会话，不是单次 HTTP 请求。模型慢、工具慢、排队慢都算在里面。作用是给用户一个上限：再怎么卡，两分钟内一定给一个明确结果，哪怕是超时中断。

### 41. 为什么 `blockedCalls` 要单独计数？

答：它是诊断信号。`toolCalls` 高说明任务复杂，`blockedCalls` 高说明模型在死循环或者提示词有问题。两个数字放一起才能定位问题，混成一个就只知道调用多。

### 42. 工具为什么是串行执行？

答：行动卡和候选记忆都是写操作，并行只会让日志交错，没有性能收益。要真并行，得先保证工具之间没有隐式依赖，比如 `ask_user` 和 `propose_action` 同时跑，提案可能基于还没答的问题。串行是保守选择。

## 证据入库

### 43. ICS 里带 TZID 的时间怎么变成 UTC？

答：`DTSTART;TZID=Asia/Shanghai:20261120T190000` 的字面量是墙钟时间，不是 UTC。做法是先把它当成 UTC 得到一个猜测值，再用 `Intl.DateTimeFormat` 按目标时区把这个猜测值格式化回墙钟，两次相减得到偏移，`UTC = 墙钟 - 偏移`。夏令时切换附近偏移会变，所以算两遍收敛。不引第三方库，是因为只需要这一处；如果以后要处理历史时区数据库，再换 `Temporal` 或 `luxon`。

为什么问：ICS 的时区是最容易写出"差 8 小时"的地方，考你有没有真的处理而不是 `new Date(string)`。

### 44. 解析失败的材料为什么落 pending_review，而不是丢掉？

答：丢掉等于静默改变证据集，用户不知道哪些材料没进来。`pending_review` 保留来源指针和失败原因，但不进快照、不参与检索，模型也读不到正文。人工用 `npm run review` 处理：接受必须有正文（截图要先补 OCR 结果），拒绝记为 `rejected`。接受的那一刻才开始计算保留期，截图 24 小时、日历 90 天，因为确认之前不能把原文清掉。这是"宁可少一条，不可多一条错的"在入库层的体现。

为什么问：考你会不会把"解析失败"当成异常日志，而不是数据状态。

### 45. 去重键为什么不用解析后的时间？

答：日历的去重键是 `UID + 原始事件块`，重复事件再加实例的墙钟标识（如 `20261111T090000`）。解析后的时间依赖解析器的时区实现，今天按 Asia/Shanghai 算，明天修了 DST bug 算出另一个 UTC，同一个事件就会被当成新证据再入一次。用墙钟标识而不是换算后的 UTC 时间戳，是同一个理由：它只取决于 ICS 里写了什么。截图用图片字节的 sha256，文件改名、重新导入都不影响。去重键要尽量只依赖原始输入，不依赖处理逻辑。

为什么问：考你知不知道"幂等键"应该建立在什么上。

### 46. 待确认的证据怎么保证模型看不到？

答：三层。快照装配时过滤掉 `pending_review`；`search_evidence` 在检索前过滤；`get_evidence_text` 拿到证据后检查状态，不是 `active` 就抛错。只做第一层不够，因为模型可以直接按 ID 读，也可以先搜再读。`listEvidence` 故意不过滤，它是给人工审核和审计用的，不是给模型用的。

为什么问：考你的权限边界是分层做的，还是只在一个地方加了个 if。

### 47. 重复日程怎么展开？为什么在入库时展开，而不是查询时展开？

答：入库时按 `RRULE` 展开成多条证据，每条实例一个 `capturedAt`。支持 `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY`，加 `INTERVAL`、`COUNT`、`UNTIL`、周规则的 `BYDAY`、月度年度的 `BYMONTHDAY`、例外日期 `EXDATE`。三个容易写错的点：一是按墙钟日历推进而不是加毫秒，夏令时切换那天"每天 9 点"才还是 9 点；二是月度和年度遇到不存在的日期跳过，1 月 31 日按月重复时 2 月没有实例，不能滑到 3 月 3 日；三是周规则带 `BYDAY` 时一周内要按距起点的天数排序，起点是周三、`BYDAY=MO,FR` 的话周五在本周、周一在下一周。`COUNT` 在排除 `EXDATE` 之前计数，这是 RFC 规定的顺序，先生成再排除。

入库时展开是为了让快照、检索、TTL 都只处理"具体某一次的日程"，查询时不用再带一份展开器。代价是展开结果是快照，不会自动往后补新实例，过期后要重新导入。窗口定在现在往后 90 天，单事件最多 120 个实例，防止"每 5 分钟重复"把库撑爆；不支持的规则（`BYSETPOS`、`BYMONTH`、`BYDAY` 的序号写法等）退化成只导入首个实例，并把原因写进正文，不静默当普通日程处理。去重键里加了实例的墙钟标识，同一事件的不同实例各自成条，重复导入仍然命中同一个键。

为什么问：重复事件是日历里最容易"看着对、其实差一天"的地方，考你有没有处理日历语义而不是只做字符串解析。

### 47.1 展开一条 2015 年开始的每日日程要多久？怎么发现的？

答：一开始 681 毫秒一条，日历里十几条重复日程就会卡住导入。慢在把每一条历史候选都做了时区换算，2015 年到现在四千多次 `Intl` 格式化。但那些日期必然在 90 天窗口之外，唯一的用途就是数 `COUNT` 名额。所以加了一个廉价判断：候选的墙钟日期早于"现在减一天"就只累加计数、不算时区。修完 39 毫秒。这类问题的共同点是正确性没问题、只在真实数据上才暴露，所以要用一条长历史的样本量一下，而不是只拿几天的测试样本。

为什么问：考你会不会把"跑通了"和"跑得动"分开看。

### 48. 截图 OCR 为什么要求模型只输出 JSON？

答：下游要的是 `capturedAt` / `title` / `content` 三个字段，让模型自由描述的话还得再写一个解析器，而且它每次的措辞都不太一样。JSON 把格式固定下来，但只提要求不够：实测模型经常套一层 markdown 代码围栏，或者先说一句"抽取结果如下"再给 JSON。所以解析器要做三件事，剥围栏、取第一个 `{` 到最后一个 `}`、逐个字段做类型和范围校验。输出格式约束和解析鲁棒性必须成对做，只做前者线上一定会遇到脏回复。

为什么问：考你有没有把"调通了"和"稳定"分开看。

### 49. OCR 失败了为什么不自动重试？

答：重试解决的是网络抖动和限流，解决不了"这张截图本身糊了或者没文字"。而且重试三次要等几十秒，人工补一句正文只要十几秒。现在的分工是模型侧只调一次，失败落 `pending_review`，人用 `npm run review -- --accept <id> --content "补上的正文"` 处理。真要加自动重试，得先把错误分成可重试（超时、429）和不可重试（缺 key、图片格式不支持），pi 现在抛出来的异常没有这层分类，所以我先不做半成品。

为什么问：考你会不会区分"能修的错误"和"修不了的输入"。

### 50. OCR 给的 capturedAt 为什么还要再校验一次？

答：模型会把"明天下午"原样抄进 `capturedAt`，`new Date("明天下午")` 得到 Invalid Date。不校验就入库，时间线会被污染，后面按时间排序和 TTL 计算都不可信。所以解析后只接受能转成合法时间的值，转不了就丢掉这个字段，让调用方回落到文件修改时间。时间宁可用一个粗糙但真实的来源，也不要用模型猜出来的假时间。

为什么问：考你会不会对一个"看起来填了"的字段保持怀疑。

### 51. 换一个视觉模型要改多少？

答：换模型设 `RELATIONSHIP_OCR_MODEL`，换供应商设 `RELATIONSHIP_OCR_BASE_URL`，前提是对方 OpenAI 兼容、支持 `image_url` 的 base64 内联。默认用的百炼 `qwen3-vl-plus`。这里踩过一个坑：一开始按文档默认 `qwen-vl-max`，结果账号下的模型列表里根本没有它，服务端回 404 Model not exist。后来先查 `GET /compatible-mode/v1/models` 看这个 key 到底能看到哪些模型，再定默认值。主模型为什么不能顺手拿来 OCR：DeepSeek V4 Pro 的模型定义里 `input` 只有 `text`，图片塞进去直接 400。key 是在 `completeSimple` 的 `options.apiKey` 里单独传的，不改 `process.env`，所以 OCR 和主 Agent 可以用两把不同的 key，也不会互相覆盖。局限是这个设计只验证过百炼一家。

为什么问：考你知不知道自己方案的适用边界，以及有没有踩过"多模态模型其实是纯文本"这种坑。

### 52. 保留期到了，模型还能不能看到原文？

答：现在看不到，但这是刚修过的。原来快照里过期证据只给摘要，可 `search_evidence` 返回的片段和 `get_evidence_text` 返回的正文都是直接取 `content`，模型换一个工具就能拿到全文。这和 `pending_review` 那次是同一类问题：只在一个入口加过滤，等于没加。现在两个工具都按 `isExpired` 判断，过期后片段和正文都换成摘要，并标 `expired: true` 和一句说明。smoke 里埋了一条带暗号的长正文，断言快照、检索、按 ID 读取三条路都拿不到暗号。

为什么问：考你的隐私策略是端到端还是一次性的 if。

### 53. 证据保留期从什么时候开始算？

答：从入库时间算，`expiresAt = 入库时刻 + TTL`。我最初按拍摄时间算，理由是防止补录旧材料把保留期重置，实际用起来发现补录一张上周的截图会一入库就过期，OCR 出来的正文当场作废，识别白跑。所以改成入库时间。代价是反复重新导入可以一直续期，但这个系统是单用户助手，导入是用户自己的显式动作，不构成威胁。保留期真正要管的是原始文字在系统里留多久，不是拍摄多久后必须清掉；图片文件本来就不在系统里，只存了 `sourceRef`。

为什么问：考你知不知道策略实际会怎么影响功能，而不是只会说"为了隐私"。

### 53.1 过期之后，模型还能拿到原始文字吗？

答：不能，而且这是修过的。快照一直按过期给摘要，但 `search_evidence` 的片段和 `get_evidence_text` 的正文原来直接取 `content`，模型换个工具就能拿到全文。现在三处都按 `isExpired` 换成摘要，并标 `expired: true`。smoke 里埋了一条带暗号的长正文，断言快照、检索、按 ID 读取三条路都拿不到暗号。

为什么问：考你的隐私策略是端到端还是一次性的 if。

## 设备接入

### 54. 从 mock 换到真实设备要改多少？

答：只写一个 `DeviceAdapter` 实现，`Outbox`、执行器、对账、崩溃恢复一行不改。契约只有三条：`execute` 把卡变成真实副作用并返回回执，`lookup` 回答"这个 requestId 你执行过没有"，查询本身失败时抛异常而不是返回"没有"。第一版接的是文件日历设备：确认后的日程和提醒写成 `.ics`，用户导入系统日历。选它是因为零凭据、零服务，却同时满足两条契约，能把"换设备只换适配器"这件事先证明出来，再去接需要网络和凭据的通道。

为什么问：考你的抽象是真的分层，还是嘴上说分层、实际到处特判。

### 55. 文件设备怎么做幂等？

答：文件名由 `requestId` 决定，`UID` 也写 `requestId`，所以同一次提案无论重试几次，设备侧只可能有一个文件。写文件先写临时文件再 `rename`，目录里出现某个 `.ics` 就意味着内容完整，不存在"写了一半被当成执行成功"的中间态。已经存在的文件不覆盖，直接返回成功回执：设备上次执行了、回执丢在路上的情况会走到重试，这时覆盖反而可能把用户已经改过的日程冲掉。

为什么问：幂等不是"加个 if 判断"，要说清楚键是什么、中间态怎么消失。

### 56. 设备查询失败为什么不能返回"没执行过"？

答：因为调用方会据此安全重发，重发的对象可能已经执行过，直接产生重复副作用。这个契约在接口注释里写死了，但真实现时还是踩了一次：Windows 上对"普通文件/子项"做 `stat` 返回的是 `ENOENT`，不是 `ENOTDIR`。照直翻译，目录不可用会被当成"设备确实没收到"，正好是最危险的那种误判。修法是 `lookup` 先检查设备目录本身在不在、是不是目录，只有目录正常才去查文件。压测里"设备不可查"那一档 96.5% 的最终一致率、7 条升级人工、重复副作用 0，守的就是这条边界。

为什么问：考你知不知道 `undefined` 在幂等查询里是一个强断言，不是"没查到"。

### 57. 为什么先做文件版，不先接企业微信或钉钉？

答：两个原因。机器人在群里发言用的是机器人身份，不是替用户发消息，和"以用户名义草拟"的产品边界冲突；而且 webhook 没有幂等查询能力，`lookup` 只能抛异常，系统会退化到"状态未知就交给人"那一档，压测数字直接从 100% 掉到 96.5%。文件版没有这些限制，还能把适配器的替换边界先验证掉。CalDAV 也已经接上，条件 `PUT` 加 `GET` 能同时演示"有查询能力"的设备，Radicale 实测 201 / 412 / 200 都符合预期。IM 通道最后决定不做，理由就是上面两条，写进 README 的范围说明。

为什么问：考你是按可验证性排优先级，还是按听起来高级排。

### 57.1 设备返回"执行成功"代表用户看到了吗？

答：不代表。文件设备只保证文件写完整了；CalDAV 只保证服务器收下了。手机什么时候拉取、用户什么时候打开日历，是客户端自己的事。这和系统里 `confirmed` / `executed` 的划分一致：`confirmed` 是用户点了确认，`executed` 是设备接受了，再往后"用户真的看到"不在追踪范围内。接 IM 的话这条边界更明显，消息接口返回成功只代表发送队列收下了。

为什么问：考你会不会把"接口 200"说成"用户收到了"。

### 58. 文件版和 CalDAV 版的幂等各靠什么？

答：文件版靠文件名，`requestId` 决定路径，`UID` 也写 `requestId`，重复执行看到文件已存在就直接返回成功，不覆盖。CalDAV 版靠 HTTP 条件写入，`PUT` 带 `If-None-Match: *`，资源存在时服务端返回 412，按"已存在"处理。两者都是把幂等交给设备侧的唯一事实来源，而不是在应用层先查一遍再写。先查再写中间有窗口，两个执行器同时进来会都查到"不存在"。

为什么问：考你的幂等是建立在存储的唯一性上，还是建立在"我记得我写过"上。

### 59. CalDAV 的 PUT 超时了，算执行失败吗？

答：不算，这是最需要想清楚的一类。超时的时候服务端可能已经收下了，系统没有任何信息区分"收下了没回包"和"根本没收到"。所以回执只能标可重试失败，交给 Outbox 重试。重试会被 `If-None-Match: *` 挡住：服务端已经有这个 UID，返回 412，适配器按成功处理。所以重试不会产生第二条事件。如果当初没用条件写入，这里只能二选一：要么冒重复写的风险，要么把卡永久留在 submitted 等人。文件版也是同一个思路，rename 之后文件存在即完整，重试直接返回成功。

为什么问：考你知不知道"超时"和"失败"不是一回事，以及幂等键能不能兜住重试。

### 60. CalDAV 只在模拟服务上验过，凭什么说能接真实日历？

答：协议层在真实服务上也验证过了。本机起了一个 Radicale，两张卡照常执行，`PUT` 返回 201；同一个 requestId 带 `If-None-Match: *` 再 `PUT` 一次返回 412，事件没有被覆盖；`GET` 返回 200，`lookup` 能查到，读回的 `UID` 和 `requestId` 一致。这说明条件写入的语义不是我们客户端自己模拟出来的。没验证的是 Nextcloud 和 iCloud：差异在 URL 怎么发现、认证方式（iCloud 要应用专用密码），以及个别服务对条件请求的返回码。这部分只能拿真实账号跑一次。还有一个边界：这类测试会往日历里写事件，所以不适合放进自动化用例。

为什么问：考你会不会把"按规范实现"讲成"已经验证过所有服务"，以及会不会用真实实现验证关键假设。

## 还没答好的问题

- 摘要以 user 角色注入，属于低强度的提示注入面。
- 36 条脚本用例全绿（比上一轮多 3 条：跨会话记忆、保留期内、保留期外）；真实模型同一天跑了十轮，固定时钟后连续三轮 12/12、11/12、12/12（35/36 = 97.2%，任务完成率每轮 7/7），放宽断言后验证轮 12/12；四轮累计 145 次调用 0 越界，95% 上界约 2.1% 且调用相关、只能当近似。新增的三条还没进真实模型批量评测。deepseek 与 qwen 的对比没跑；`sourceIds` 只校验归属不校验内容支撑。
- 语义 Judge 已实现（规则 + LLM 两种，共用接口），校准工具也写好了（`judge --out` + `calibrate`），但没有人工打分数据，也没跑过真实模型全量语义评测；分数只能同 rubric 内比较。
- 跨会话用例是两段会话紧接着跑，测不出"隔一周还能不能想起来"，也没有遗忘和冲突合并场景。
- prompt cache 只跑过一次冷启动（24 轮），没换窗口参数和模型做敏感性分析。
- 探针每臂 10 题跑一次，只能看方向。
- `recall_history` 仍然是子串匹配，不分词、不按相关性排序。
- 压缩只在每次 LLM 调用前触发，没有后台任务。
- 洞察 Agent 和主 Agent 可能提出重复候选，没有按文本去重。
- `executeConfirmed` 每次全表扫，`applyCandidate` 只重试两次。
- `pending_review` 的审核是命令行，没有界面；接受空正文的截图必须先手工补 OCR 结果。
- 复杂重复规则（`BYSETPOS` / `BYMONTH` 等）不展开，只导入首个实例；展开结果不随日期推移自动补新实例。
- 真实设备做了文件日历和 CalDAV，IM 通道（企业微信 / 钉钉）没接；CalDAV 在 Radicale 上验过条件写入和幂等查询，Nextcloud / iCloud 的 URL 发现与认证差异没跑过。
- 截图 OCR 没有标注集，准确率只能靠手跑几张图看；`confidence` 只打印，不参与判定。
